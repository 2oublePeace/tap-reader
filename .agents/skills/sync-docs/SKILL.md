# Навык: Синхронизация проектной документации (Docs-as-Code Sync)

Данный навык запускается, когда разработчик просит «актуализируй доку», «обнови документацию перед пушем», «sync docs», либо перед отправкой изменений в удаленный репозиторий.

---

## Пошаговый алгоритм выполнения

### Шаг 1. Анализ измененных файлов
1. Запустите команду `git status -s` и `git diff --name-only`, чтобы увидеть все модифицированные, новые или удаленные файлы относительно последнего коммита или ветки `main`.
2. Сгруппируйте изменения по модулям проекта:
   - `:features:<name>`
   - `:core:<name>`
   - `:shared`
   - Корневые конфигурации (`build-logic`, `gradle`)

### Шаг 2. Актуализация паспортов модулей (`README.md`)
Для каждого затронутого модуля:
1. Прочитайте текущий паспорт модуля `README.md`.
2. Если изменился публичный контракт (`api/`):
   - Обновите раздел **«2. Публичный контракт (`api/`)»** актуальными сигнатурами интерфейсов, фабрик или моделей стейта.
3. Добавьте запись в раздел **«История изменений модуля (Recent Changes)»**:
   - Формат: `* **ГГГГ-ММ-ДД (TP-<номер>):** Краткое описание изменений ([ADR-XXXX] если применимо)`.

### Шаг 3. Проверка необходимости ADR
Проанализируйте характер изменений:
* Были ли подключены новые фундаментальные библиотеки?
* Было ли принято решение с компромиссом (trade-off) или изменен существующий архитектурный паттерн?
* Если **ДА** $\rightarrow$ подготовьте черновик `docs/adr/XXXX-<slug>.md` по шаблону [template.md](../../../docs/adr/template.md) и предложите пользователю зафиксировать его.
* Если **НЕТ** (обычная реализация логики/экрана) $\rightarrow$ переходите к следующему шагу без создания лишних документов.

### Шаг 4. Актуализация журнала изменений (`CHANGELOG.md`)
1. Откройте [docs/changelog/CHANGELOG.md](../../../docs/changelog/CHANGELOG.md).
2. В секцию **`## [Unreleased]`** добавьте описание сделанного в соответствующую подсекцию:
   - `### Added` — новые фичи или экраны.
   - `### Changed` — изменение поведения существующих компонентов.
   - `### Fixed` — исправление багов.
   - `### Removed` — удаление устаревших абстракций.

### Шаг 5. Формирование сообщения коммита
Сформируйте идеальное сообщение коммита по стандарту [gitflow.md](../manifests/gitflow.md):
```text
<type>(TP-<номер>): <краткое описание сделанного> [ADR-XXXX]
```
*Напоминание:* Не создавайте отдельных коммитов на исправление опечаток в документации — объединяйте их через `git commit --amend` или включайте в состав основного коммита задачи.
