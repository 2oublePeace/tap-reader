# Манифест Документации: Docs-as-Code, регламент ведения ADR, RFC и паспортов модулей

Данный манифест регламентирует жизненный цикл проектной документации в проекте **TapReader**. Документация является первоклассным инженерным артефактом: она пишется в Markdown, хранится в Git рядом с кодом и обновляется синхронно с изменениями в архитектуре.

---

## 1. Архитектурные решения (ADR — Architecture Decision Records)

Каталог: [`docs/adr/`](file:///home/emiryanvl/Проекты/tapreader/docs/adr/)  
Шаблон: [`docs/adr/template.md`](file:///home/emiryanvl/Проекты/tapreader/docs/adr/template.md)

### Когда обязательно создается ADR (Триггеры):
1. **Выбор фундаментальных библиотек и инструментов:** Decompose vs Voyager, Koin vs Metro, Ktor vs Retrofit, Room vs SQLDelight.
2. **Архитектурные развилки и паттерны:** Решение о структуре модулей, разделении `api/impl`, переходе на MVI State Hoisting, обработке ошибок.
3. **Принятие решений с компромиссами:** Когда мы сознательно жертвуем одним ради другого (например: чуть больше бойлерплейта Screen/Content ради нативного SwiftUI на iOS и тестов на JVM).
4. **Отказ от ранее принятых решений (Superseding):** Кардинальная смена подхода.

### Правило неизменяемости ADR:
* ADR — это **исторический протокол**. Принятый ADR **не переписывается задним числом**.
* Если через полгода мы меняем подход:
  1. Создается новый документ, например `0005-new-approach.md` со статусом `Accepted`.
  2. В старом `0001-...md` статус меняется на `Superseded by ADR-0005`.

## 2. Проектирование фичей (RFC — Request for Comments)

Каталог: [`docs/rfc/`](file:///home/emiryanvl/Проекты/tapreader/docs/rfc/)  
Шаблон: [`docs/rfc/template.md`](file:///home/emiryanvl/Проекты/tapreader/docs/rfc/template.md)

### Когда пишется RFC:
* **Перед стартом нетривиальных функциональных блоков (Epic):** Движок парсинга книг и пагинации, система контекстного перевода и подсветки идиом, оффлайн-словарь, синхронизация прогресса чтения.
* **Цель:** Согласовать стейт-машину, структуру БД, контракты API и краевые случаи (edge cases) **до** написания кода.
* **Связка с трекером:** В заголовке RFC указывается ключ задачи `TP-XXX`. Раздел `Implementation Tasks` служит источником для создания атомарных подзадач в трекере.

## 3. Модульные паспорта (`README.md` в модулях)

Каждый Gradle-модуль проекта обязан содержать файл `README.md` на одном уровне с `build.gradle.kts`.

### Обязательные разделы паспорта:
1. **Зона ответственности:** Для чего существует модуль в 2–3 предложениях.
2. **Публичный контракт (`api/`):** Ключевые интерфейсы, фабрики, экраны и DI-модули.
3. **Внутренняя реализация (`impl/`):** Особенности Decompose-логики, Domain-слой, верстка.
4. **Граф зависимостей:** От кого зависит модуль и кто зависит от него.
5. **История изменений (Recent Changes):** Хронологический список ключевых доработок модуля со ссылками на тикеты `TP-X` и связанные ADR.

### Правило синхронной актуализации:
Если задача меняет публичный контракт модуля (сигнатуру фабрики, модель состояния, DI), разработчик и ИИ-агент обязаны **в том же коммите/PR** обновить `README.md` соответствующего модуля.

## 4. Журнал релизов (`docs/changelog/CHANGELOG.md`)

* Ведется строго по международному формату [Keep a Changelog](https://keepachangelog.com/) и SemVer.
* Все незарелизенные доработки фиксируются в блоке `## [Unreleased]`.
* Изменения группируются по типам: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.

---

## 5. Проактивное поведение ИИ-агента

При парном программировании ИИ-агент обязан соблюдать проактивный протокол:

1. **Инициатива по ADR:** Если в диалоге с разработчиком принимается фундаментальное или нетривиальное решение, агент обязан предложить:
   > *«Мы только что согласовали важное архитектурное решение по [X]. Предлагаю зафиксировать его в ADR-XXXX. Я могу подготовить проект документа»*.
2. **Инициатива по RFC:** При поступлении задачи на разработку крупного функционального блока агент предлагает:
   > *«Задача комплексная. Предлагаю сначала составить RFC-черновик с моделями данных и стейт-машиной, а после согласования перейти к коду»*.
3. **Контроль актуальности:** При рефакторинге или изменении контрактов агент автоматически обновляет соответствующие модульные паспорта и чейнджлог.

## 6. Строгая гигиена Git и запрет микро-коммитов

* Запрещено засорять историю Git отдельными коммитами на исправление опечаток в документации (`docs: поправил опечатку`).
* Правки вносятся через `git commit --amend` или объединяются с плановыми коммитами задач.
