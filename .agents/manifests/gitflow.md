# Манифест Gitflow: Стандарт коммитов, веток и связывания с документацией

Данный манифест регламентирует правила оформления Git-коммитов, декомпозиции веток и связывания кода с задачами в трекере и архитектурными решениями в проекте **TapReader**.

---

## 1. Система «3 Бакета» и формат сообщения коммита

Вся разработка в проекте строго делится на три бакета. Коммиты оформляются с указанием бакета и ключа задачи в круглых скобках:

```text
<type>(TP-<номер>): <краткое описание> [дополнительные теги]
```

### Допустимые типы (`<type>`):
1. **`feature`** *(Продуктовый бакет / Product Bucket)*:
   - Новая продуктовая функциональность, пользовательские экраны, бизнес-логика и сопутствующая документация фичи.
2. **`tech`** *(Технический бакет / Tech Bucket)*:
   - Любое техническое развитие проекта: архитектура, подключение библиотек, рефакторинг, настройка Gradle и CI/CD, написание тестов, а также работа над манифестами и ADR.
3. **`fix`** *(Саппорт бакет / Support Bucket)*:
   - Исправление багов, крашей и проблем пользователей.

> **Важно:** Отдельные префиксы вроде `docs`, `chore`, `refactor`, `test` **не используются**. Любая документация, тесты и рефакторинг всегда выполняются и коммитятся в рамках своей продуктовой (`feature`), технической (`tech`) или багфикс (`fix`) задачи.

### Структура остальных полей:
* **`(TP-<номер>)`** — краткий ключ задачи из таск-трекера (например, `TP-1`, `TP-42`).
* **`<краткое описание>`** — понятное описание сделанного в повелительном наклонении (что сделать: *«добавить...»*, *«перевести...»*, *«исправить...»*).
* **`[дополнительные теги]` (опционально):**
  * Если в рамках коммита создается или реализуется архитектурное решение (ADR) или спецификация (RFC), в конце строки обязательно указывается тег:
    `[ADR-0001]`, `[RFC-0002]` или `[ADR-0001, RFC-0002]`.

### Примеры правильных коммитов:
```text
tech(TP-1): перевести Decompose-компоненты на Pure Kotlin [ADR-0001]
tech(TP-1): настроить инфраструктуру Docs-as-Code и зафиксировать ADR-0001 [ADR-0001]
feature(TP-2): реализовать экран создания привычки [RFC-0001]
fix(TP-15): исправить мерцание при переключении дочерних экранов
```

## 2. Строгий запрет мусорных микро-коммитов (Anti-Typo Rule)

❌ **Категорически запрещены** коммиты вида:
* `поправил опечатку в ADR`
* `исправил запятую`
* `мелкие правки`

### Как правильно исправлять опечатки и неточности:
1. **Дополнение последнего коммита (`--amend`):**
   Если опечатка замечена до отправки ветки в удаленный репозиторий:
   ```bash
   git add .
   git commit --amend --no-edit
   ```
2. **Интерактивный ребейз (`fixup`):**
   Если правка относится к более раннему локальному коммиту ветки:
   ```bash
   git commit --fixup <хэш-коммита>
   git rebase -i --autosquash <базовая-ветка>
   ```
3. **Объединение с плановым коммитом:**
   Если неточность найдена в документации задним числом, она правится попутно в рамках следующего планового коммита задачи.
4. **Squash and Merge:**
   При необходимости промежуточные коммиты ветки склеиваются при вливании в основную ветку.

## 3. Стандарт именования и декомпозиции веток (Branch Naming)

Ветки создаются по трехсоставному шаблону с поддержкой порядковой декомпозиции внутри задачи:

```text
<тип>/TP-<номер-задачи>/<номер-ветки>-<краткое-название>
```

### Поля названия ветки:
* **`<тип>`** — один из трех бакетов: `feature`, `tech` или `fix`.
* **`TP-<номер-задачи>`** — идентификатор задачи в трекере (например, `TP-1`).
* **`<номер-ветки>`** — порядковый индекс подветки в рамках задачи (начиная с `0`: `0`, `1`, `2`...).
  * *Зачем нужен индекс:* Когда задача объемная, мы декомпозируем её на последовательные этапы (ветки). Индекс гарантирует хронологическую сортировку веток в IDE и Git и сразу показывает порядок их вливания.
* **`<краткое-название>`** — слаг на английском языке через дефис, отражающий суть конкретного этапа.

### Примеры декомпозиции задачи на ветки:
```text
// Задача TP-1 разбита на последовательные этапы:
feature/TP-1/0-add-project-architecture
feature/TP-1/1-setup-decompose-navigation
feature/TP-1/2-implement-profile-screen

// Техническая задача TP-4:
tech/TP-4/0-configure-room-database

// Багфикс TP-15:
fix/TP-15/0-fix-timer-notification-leak
```
