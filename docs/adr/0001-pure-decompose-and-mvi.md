# ADR-0001: Использование Pure Kotlin Decompose компонентов и MVI State Hoisting

* **Статус:** Accepted
* **Дата:** 2026-10-12
* **Автор(ы):** @emiryanvl, AI Assistant
* **Задача в трекере:** TP-1

---

## 1. Контекст и проблематика (Context)

На начальном этапе создания проекта возник вопрос организации Decompose-компонентов и их взаимодействия с Jetpack / Multiplatform Compose.

Ранее в ряде проектов применялся подход жесткой инкапсуляции UI через паттерн `RenderableComponent`:
* Компонент реализовывал интерфейс `Renderable` с методом `@Composable fun Render(modifier: Modifier)`.
* Внутреннее состояние экрана (`State`) было полностью приватным и скрытым в реализации (`impl`).
* Публичный интерфейс компонента не имел доступа к состоянию и отдавал наружу только функцию отрисовки.

Однако при проектировании масштабируемого KMP-приложения TapReader выявились существенные ограничения такого подхода:
1. **Невозможность нативного UI на iOS:** Если экран на iOS понадобится реализовать на нативном SwiftUI, интерфейс с методом `Render()` бесполезен, так как завязан на Compose Multiplatform рантайм, а состояние скрыто.
2. **Сложность Unit-тестирования:** Невозможно протестировать изменение состояния экрана в чистом, мгновенном JVM-тесте без запуска эмулятора или Compose-тест-раннера.
3. **Нарушение Compose Previews:** Если Composable-функция жестко привязана к живому инстансу компонента (`componentContext`, DI, корутины), ее невозможно запустить в `@Preview` в Android Studio.

---

## 2. Рассмотренные альтернативы (Alternatives Considered)

### Вариант 1: Паттерн «RenderableComponent» (Инкапсулированный рендер)
* **Описание:** Компонент реализует `@Composable fun Render(modifier: Modifier)`. Состояние скрыто внутри.
* **Плюсы:** Высокая инкапсуляция в рамках одного Compose-приложения, компоненты можно прокидывать как «слоты».
* **Минусы:** Жёсткая связка с Compose рантаймом, невозможность работы со SwiftUI на iOS, невозможность быстрых JVM-тестов на состояние.
* **Причина отклонения:** Блокирует будущую кроссплатформенную эволюцию и качественное тестирование логики.

### Вариант 2: Pure Kotlin Decompose + MVI State Hoisting (Выбранный вариант)
* **Описание:** 
  1. Интерфейс компонента — чистый Kotlin (ноль Compose-импортов).
  2. Публичный реактивный поток состояния `val state: Value<T>` (read-only срез).
  3. Единая точка входа для событий `fun onIntent(intent: XIntent)`.
  4. Разделение UI на два уровня: Stateful `XScreen(component)` и Stateless `XContent(state, onIntent)`.
* **Плюсы:** 
  - Полная свобода от UI-рантайма на уровне бизнес-логики.
  - Мгновенные тесты логики на JVM (5 мс).
  - Нативная интеграция со SwiftUI на iOS через `component.state.asObservableObject()`.
  - Полноценная поддержка `@Preview` и скриншот-тестирования для `XContent`.
* **Минусы:** Наличие двух Composable-функций (`Screen` и `Content`) на каждый экран.

---

## 3. Принятое решение (Decision)

Мы решили:
1. **Очистить интерфейсы компонентов от UI-зависимостей:** В `*Component` запрещены аннотации `@Composable`, `Modifier` и методы `Render()`.
2. **Публиковать read-only состояние:** `val state: Value<XState>` является частью публичного контракта компонента. Мутируемый `MutableValue` строго инкапсулирован в `*ComponentImpl`.
3. **Использовать MVI Intent:** Запрещено плодить в интерфейсе компонента десятки разрозненных методов (`fun onRefresh()`, `fun onAction()`). Все действия передаются через `sealed interface XIntent` и метод `fun onIntent(intent: XIntent)`.
4. **Разделять UI (State Hoisting):**
   - `*Screen` (Stateful Container, `public` в `api`): связывает компонент с UI, подписывается на `component.state` и делегирует `component::onIntent`.
   - `*Content` (Stateless Layout, `internal` в `impl/ui`): чистая верстка, принимающая `State` и `(XIntent) -> Unit`, сопровождаемая приватными `@Preview`.
5. **Изолировать навигацию:** Компоненты фичей ничего не знают о других экранах. Навигация наружу делегируется родительскому роутеру через лямбды в `Factory`.

---

## 4. Последствия и компромиссы (Consequences)

### Положительные (Плюсы)
* Логика компонентов тестируется на JVM без эмуляторов и Compose.
* Проект готов к созданию нативного iOS UI на SwiftUI в любой момент без переделки общего кода.
* Верстка легко покрывается Compose Previews и Paparazzi/Roborazzi скриншот-тестами.
* Единая точка обработки интентов (`onIntent`) упрощает аналитику, логирование и отладку.

### Отрицательные / Компромиссы (Минусы)
* Для простых экранов создание пары `Screen` + `Content` создает небольшой дополнительный бойлерплейт, который, однако, полностью окупается при масштабировании.
